# Tay 2.0: конфігурація, recovery і compaction

Статус: Engine використовує `RECOVERY`; online checkpoint інкрементальний
також після зміни tail та retention. Формат 2 публікує корені jobs, робочих
задач, schedules, results та строків retention. Незмінні сторінки індексів і
сегменти залишаються у своїх epoch; checkpoint додає лише змінені шляхи дерев,
нові snapshots та актуальний робочий стан. Перший checkpoint старого формату
атомарно створює новий формат через звичайну публікацію CURRENT.

Очищення вибирає до 16 розріджених сегментів із сукупним input до 64 MiB за
автентифікованими live-byte summaries. Це порція роботи, не квота історії.
Сегмент підлягає перепакуванню, якщо застарілі байти займають принаймні
половину. Досяжність із п'яти коренів і native reader pins захищають спільні
файли. Фоновий GC перевіряє CURRENT перед кожною порцією видалень; збій
відкладає очищення, не скасовує публікацію. Backup/restore копіює також усі
досяжні файли старших epoch і перевіряє їх каталогом SHA-256.

Поточні межі: startup ще обходить terminal metadata для disposable DETS та
індексів перегляду; results залишаються в пам'яті. Повністю незалежний від
кількості архівних ID startup і дискові Dashboard facets — окремий наступний
етап. Нижче ці цілі позначені як цільова архітектура, а не досягнуті гарантії.

## Принцип публічного конфігу

Користувач задає політику: де зберігати дані, що виконувати, конкуренцію черг,
строк збереження історії, адреси й TLS, доступні ресурси та потрібні таймаути.
Параметри алгоритму обробки, розміри внутрішніх порцій і пороги запуску
обслуговування визначає Tay.

Видалення налаштування не повинне замінювати його прихованим обмеженням
користувацьких даних. Фізичні межі формату, обмеження файлової системи та
облік доступної пам'яті залишаються явно описаними контрактами.

## Виконане видалення параметрів

| Видалений параметр | Заміна у 2.0 |
| --- | --- |
| `recovery.max_directory_entries` | Інвентар каталогу читається сторінками через native protocol v2 без загальної квоти файлів; діють ownership, перевірка незмінності й deadline. |
| `rotation_target_bytes` | Сховище визначає ротацію всередині Tay; параметра немає ні в Engine, ні у Writer, ні в джерелі Publisher. |
| `journal.batch.max_events` | Уже прийняті команди групуються автоматично; внутрішня порція обмежує тривалість одного проходу, а не кількість прийнятих задач. |
| `journal.batch.interval_ms` | Налаштовуваного очікування немає. Batch підтверджується тільки після sync; під час активного виконання вікно ingress скорочується для своєчасного refill. |
| `compaction.check_interval` | Tay сам планує перевірки обслуговування й враховує checkpoint interval. |
| `compaction.min_interval` | Пауза залежить від виміряної тривалості попередньої операції, а не окремого таймера конфігурації. |
| `compaction.min_sealed_segments` | Публічного порогу немає; для reclaim потрібна наявність sealed history. |
| `compaction.min_reclaimable_bytes` | Очікуване звільнення порівнюється з оцінкою байтів переписування retained candidate. |
| `compaction.dead_ratio_threshold` | Окремого коефіцієнта немає; рішення базується на вартості переписування та користі очищення. |
| `compaction.enabled` | Для вимкнення автоматичного обслуговування залишається лише compaction: false. |
| `max_insert_payload_bytes` | Окрему межу 1 MiB прибрано. Event кодується в межах фізичного формату; запити ділять спільний client_bytes без статичної квоти на слот. |

`compaction.terminal_retention` залишити: це явна політика видалення історії.
`compaction.checkpoint_interval` на першому етапі залишити єдиним часовим
параметром checkpoint: він задає періодичність збереження робочого стану,
тоді як наведені вище пороги є деталями реалізації. Це періодичність спроб,
не жорстка гарантія максимального часу між двома успішними публікаціями.

Для storage durability прибрано публічний вибір `:write`/`:sync` у production:
там уже дозволений тільки `:sync`. Development/test builds і low-level storage API зберігають явний режим
для тестів і benchmark; production Engine не приймає цей параметр. Глобальна політика durability задач
`:persistent`/`:volatile` має інше призначення і залишається.

Параметри таблиці видалено з Engine/Storage/foundation конфігурації,
standalone та benchmark CLI. Native protocol v2 читає inventory порціями без
загальної квоти; `client_bytes` є спільним бюджетом, а не поділом на слоти.
Compaction планує перевірки всередині Tay, враховує виміряну тривалість
попередньої операції та порівнює reclaim benefit з вартістю candidate rewrite.

## Параметри, які залежать від перебудови recovery

| Поточні параметри | Умова спрощення |
| --- | --- |
| `executor_result_bytes` | Результати повинні читатися з диска адресно. Потрібно переробити резерв успішного completion перед START: зараз параметр визначає і memory reserve, і journal headroom. Просте видалення змінює гарантії завершення задач. |
| `executor_error_bytes` | Прибрати окрему квоту діагностики після узгодження кодування діагностики, completion та транспортних повідомлень. |
| `executor_max_frame_bytes`, `http_max_body_bytes` | Узгодити з єдиними правилами кодування та бюджетом приймання. JSON body, executor frame і storage record мають різні накладні витрати, тому одного механічного перейменування недостатньо. |
| `executor_max_tasks_per_connection` | Внутрішню кількість призначень можна виводити з оголошеної місткості воркера та конкуренції черг; це не ліміт кількості збережених задач. |
| `client_slots`, `client_bytes` | Обидва бюджети поки залишаються, але байти вже спільні між запитами: статичний поділ на слоти прибрано. |

`executor_max_connections` зараз справді обмежує відкриті підключення, а не є
невикористаним параметром. Його можна зробити автоматичним після появи спільного
обліку пам'яті та файлових дескрипторів; видаляти перевірку без заміни не слід.

## Що залишити

- `data_dir`, `name`, `workers`, `queues`, `rate_limits`, `start_paused`.
- Політику persistent/volatile задач і `compaction.terminal_retention`.
- Параметри підключення до executor/HTTP, дозволи Unix socket та TLS.
- `max_state_bytes` і `max_history_bytes`: це реальні загальні бюджети пам'яті
  й журналу, а не довільна кількість задач чи глибина вкладення аргументів.
- `caller_timeout`, `storage_timeout`, `recovery.deadline_ms`: вони обмежують
  різні види очікування. Швидкий recovery сам по собі не робить їх дублікатами.
- Явну ініціалізацію сховища. Вимогу підтримуваної файлової системи та ownership
  не послаблювати; можливе автоматичне визначення не повинне зводитися до
  безумовного встановлення `validated_filesystem: true`.

## Швидкий recovery

Для старих checkpoint Reader створює повний `candidate.jobs/results/schedules`.
Для розширеного індексу він залишає terminal args на диску. Engine після
activation ще створює disposable terminal DETS з metadata та індекси перегляду;
startup залежить від кількості retained ID і розміру результатів.

Цільова структура:

1. Робочий checkpoint: активні задачі, стан розкладів і їхніх активних occurrence,
   логічні revision, execution/availability координати та межа застосованого журналу.
2. Незмінні архівні сегменти: завершені задачі, аргументи та результати.
3. Постійні дискові індекси: job ID, порядок перегляду, потрібні metadata/facets
   і адреси результатів. Корені й агреговані лічильники публікуються разом із
   checkpoint; для `ready` не перебираються всі архівні ID.
4. Tail після checkpoint з єдиним порядком durable змін.

Startup перевіряє authority та корені індексів, завантажує робочий checkpoint
і застосовує tail. Якщо tail повторно запускає архівну задачу, її стан читається
адресно через індекс і переходить у робочий набір. Перевірки duplicate ID,
revision, execution token і availability order не можуть зникнути через lazy read.

Dashboard читає сторінки архіву через індекси. Пошук job/result не повинен
приховано запускати повний replay. Збереження великого result не повинне
вимагати його постійного утримання у `state.results`.

Цілісність: незмінні сторінки/блоки мають контрольні суми, прив'язані до
опублікованих коренів індексів. Активні дані та metadata перевіряються до ready;
холодні дані — при адресному читанні. Пошкодження не повертається як not_found
або порожня історія. Окремий повний scrub може перевіряти весь архів, не
перетворюючи кожен startup на повне сканування. Це свідома зміна моменту
виявлення пошкодження порівняно з попереднім повним startup replay.

## Compaction

Builder читає робочий індекс і заморожений новий tail. Архівні задачі,
яких торкнувся tail, завантажуються адресно. Прострочені ID читаються з дерева
`terminal_at + job_id` до cutoff, без обходу решти архіву. Зміни кількох ключів
одного leaf застосовуються разом; незмінні шляхи не переписуються.

Частий checkpoint та очищення мають різну вартість. Checkpoint змінює лише
потрібні snapshots/шляхи; cleaner додатково переносить живі records вибраних
розріджених сегментів. Обидві операції готуються до admission fence.
Під час fence записується обмежений фінальний delta і атомарно змінюється
CURRENT. Нові сторінки й records перевіряються незалежним читачем; успадковані
посилання мають hashes від уже опублікованих коренів. Повний inspect/backup
робить scrub досяжних файлів та звіряє jobs/work/expiry.

Попередній epoch залишається, доки містить досяжні сторінки або сегменти.
Native GC виконує не більше 32 видалень / 128 переглянутих entries за запит,
перевіряє authority та pinned descriptors і синхронізує каталоги після unlinks.
Після restart очищення запускається знову. Відкладене очищення старих epoch
не входить у synchronous `reclaimed_bytes` поточного checkpoint.

`candidate_bytes` — логічні дані candidate разом із повторно використаними
сегментами; `rewritten_bytes` — нові логічні записи, а `reused_bytes` — спільні
data segments. Це не фізичні device writes. `cleaned_segments` і
`cleaned_source_bytes` показують вибрану порцію перепакування. Пауза включає
Engine adoption та повернення admission.

## Послідовність і критерії готовності

1. Специфікувати формат робочого checkpoint, архіву, індексів і їхні корені
   цілісності; визначити атомарну міграцію старого Store-v2.
2. Реалізувати адресне читання jobs/results і сторінок історії, потім підключити
   їх до recovery та Dashboard. Холодний індекс має переживати restart.
3. Додати перевикористання сегментів, reader pins та фонове очищення.
4. Прибрати наведені конфігурації, очищаючи Engine, standalone env, CLI, docs,
   benchmarks і тести. Не відновлювати їх під новими іменами.
5. Після реалізації перевірити адресний retry, duplicate ID, schedules/results,
   retention, corruption, ENOSPC, SIGKILL, lost-CURRENT reply та concurrent writes.

Вимірювання мають відділяти active state і tail від архіву. При незмінному
робочому наборі збільшення холодного архіву не повинне спричиняти читання всіх
його bodies або ID перед ready. Частий checkpoint не має переписувати незмінний
архів. Startup read bytes, peak RAM, pause і реально переписані compaction bytes
мають підтвердити це на macOS :write і Linux :sync; самих unit tests недостатньо.

Результати перевірок і сирі вимірювання: [checkpoint 2.0 evidence](evidence/checkpoint-2.0/README.md).
